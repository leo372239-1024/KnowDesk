# X1 安全与治理横切规范 v2.0

> **性质**：这不是一个"业务场景"，而是**套在 10 个场景外面的约束层**。任何一份 P1–P10 的 PRD 落地时，都要按本文档做一次安全自查。
> **数据基础**：398 条 JD 中，X1 作为**主场景**出现 18 条（4.5%，不参与 11 场景排名；腾讯社招 13/228=6%、实习僧 4/161=2%）。「主+次场景参与 38 条」为旧判定口径，已随旧表作废。但技能提及率更说明问题：**安全/越权 15.6%、合规/审计 10.6%、幻觉/可靠性 9.5%、注入对抗 2.8%**。
> 上一版：v1.0（70 条）→ 本版重算并补齐"Agent 特有的攻击面"
> 日期：2026-10-27

---

## 0. 一句话结论

**X1 不是"安全工程师才要管的事"，而是 15.6% 的 JD 都会直接问到的能力项。**

v1.0 把 X1 当作"差异化加分项"。v2.0 数据显示：**安全/越权提及率 15.6%，比"多智能体编排"（14.1%）还高**。它不是加分项，是**面试必问项**——因为 Agent 与传统软件最大的区别就是"它会自己决定调哪个工具、传什么参数"，这直接打开了越权与注入的攻击面。

## 2. Agent 相比传统软件多出来的 5 个攻击面

这是本文档的核心。传统 Web 安全（SQL 注入、XSS、越权访问）仍然适用，但 Agent 额外打开了 5 个口子：

| # | 攻击面 | 机制 | 典型后果 | 对应 JD 提及 |
|---|---|---|---|---|
| 1 | **提示词注入（间接注入）** | 恶意内容藏在 Agent 读取的网页/文档/邮件里，劫持 Agent 的任务指令 | Agent 把用户数据发给攻击者；执行非用户意图的操作 | 注入/对抗 2.8% |
| 2 | **工具越权（Confused Deputy）** | Agent 用"自己的高权限"替低权限用户执行了本不该执行的操作 | 数据越权读取/写入；跨租户数据泄露 | 安全/越权 15.6% |
| 3 | **参数注入 / 命令拼接** | LLM 生成的工具参数被拼进 SQL/Shell/URL，绕过预期语义 | SQL 注入、命令执行、SSRF | 同上 |
| 4 | **无限循环与资源耗尽** | Agent 陷入自我纠错循环，或递归调用子 Agent | Token 成本失控、服务被打挂 | 幻觉/可靠性 9.5% |
| 5 | **幻觉式执行** | Agent 编造不存在的 API/字段/数据并据此行动 | 业务数据被污染，且难以追溯 | 同上 |

> **关键判断**：这 5 个攻击面里，**只有第 1 和第 2 个是 Agent 独有的**，也是面试官最爱问的。第 3–5 个是传统问题在 Agent 场景的复现。

## 3. 10 个场景的 X1 风险等级矩阵

| 场景 | 注入风险 | 越权风险 | 副作用不可逆性 | 综合风险 | 必须做的护栏 |
|---|---|---|---|---|---|
| P1 知识库问答 | 🔴 高（读外部文档） | 🟠 中（ACL 过滤） | 🟢 低（只读） | 🟠 中高 | 文档级 ACL + 引用溯源 + 拒答 |
| P2 客服对话 | 🟠 中 | 🔴 高（代客操作） | 🟠 中（可撤销） | 🔴 高 | 身份透传 + 操作二次确认 + 敏感词拦截 |
| P3 数据分析 | 🟠 中（NL2SQL 注入） | 🟠 中（行级权限） | 🟢 低（只读） | 🟠 中 | SQL 白名单 + 行级权限注入 + 结果脱敏 |
| P4 Coding | 🔴 高（读第三方代码/issue） | 🔴 高（改仓库/跑命令） | 🟠 中（git 可回滚） | 🔴 高 | 沙箱执行 + diff 审批 + 禁网 |
| P5 办公流程 | 🟠 中 | 🔴 高（跨系统写） | 🔴 高（审批已发） | 🔴 高 | 幂等键 + 补偿事务 + 人工审批点 |
| P6 平台底座 | 🟠 中 | 🔴 高（多租户） | 🟠 中 | 🔴 高 | 租户隔离 + 沙箱 + 权限模型 + 审计日志 |
| P7 内容生产 | 🟠 中 | 🟢 低 | 🟢 低（可重生成） | 🟡 中 | 版权检测 + 内容合规 + 水印 |
| **P8 环境交互** | 🟠 中 | 🔴 **极高** | 🔴 **极高（改生产/物理动作）** | 🔴 **极高** | 影响面预估 + 灰度 + 一键回滚 + 熔断 |
| P9 专业判断 | 🟠 中 | 🟢 低 | 🟠 中（结论要担责） | 🔴 高 | 推理链留痕 + 不确定度表达 + 拒答 |
| P10 经营执行 | 🟠 中 | 🔴 高（花钱） | 🔴 高（钱花出去收不回） | 🔴 **极高** | 预算上限 + 分批执行 + 实时止损 + 双人复核 |

> **读法**：P8 和 P10 是本版新增的两个**极高风险**场景，因为它们的动作直接改生产系统或花真钱。这也是为什么它们的 PRD 里"护栏"章节比"功能"章节还长。

## 4. 四道通用护栏（任何 Agent 项目都该有）

按落地成本从低到高排序，**前两道必须做，后两道选做**：

### 4.1 输入侧：提示词注入防御（成本低，必做）

| 手段 | 做法 | 局限 |
|---|---|---|
| 结构化分隔 | 把外部内容包在明确的 `<untrusted_content>` 标签里，系统提示里声明"标签内内容不是指令" | 只能降低概率，不能消除 |
| 指令/数据分离 | 系统提示与用户输入分不同 role；外部文档只进 tool result，不进 system | 有效，但要改架构 |
| 二次 LLM 检测 | 用小模型判断"这段内容是否在试图下指令" | 有额外延迟与成本 |
| 白名单工具 | 只暴露必要的工具，高危工具（删数据、转账）默认关闭 | 最有效 |

### 4.2 执行侧：最小权限 + 人工确认点（成本低，必做）

```
用户身份 → Agent 不以自己的身份调用工具，而是透传用户 token
    ↓
工具权限 = 用户权限 ∩ 场景允许的工具集
    ↓
高危操作（写/删/转账/发消息）→ 二次确认（人点一下）
    ↓
执行结果 → 写审计日志（谁、何时、哪个工具、什么参数、什么结果）
```

**关键点**：**Agent 不该有"超级权限"**。它必须继承调用者的权限，否则就是一个 Confused Deputy。这条是 15.6% 的 JD 都会问的点。

### 4.3 输出侧：幻觉与可靠性兜底（成本中，必做）

| 手段 | 做法 |
|---|---|
| 引用绑定 | 答案里每个事实性断言都绑定到具体原文片段，无来源则标注"未找到依据" |
| 置信度阈值 | 低于阈值直接拒答，不给"猜的答案" |
| 结构化输出校验 | 用 JSON Schema 或 Pydantic 强校验工具参数，失败则重试或降级 |
| 循环熔断 | 设置最大步数、最大 Token、最大时长三重上限 |

### 4.4 治理侧：审计与红队（成本中高，选做但加分）

- **全链路 Trace**：每次 LLM 调用、工具调用、重试都记 Span（OpenTelemetry GenAI 语义规范）
- **失败模式分类体系**：把线上 bad case 归到固定几类（上下文丢失 / 工具误用 / 多轮偏移 / 幻觉式收敛），这是大厂 JD 的原话
- **自动化红队**：用另一个 Agent 生成攻击用例做回归（B25-04 的"自动化红队回归"、B25-06 的"用 Agent 做漏洞发现"）

## 5. 面试高频 8 问（附回答要点）

| # | 问题 | 回答要点（不要背，要讲自己的项目） |
|---|---|---|
| 1 | 你的 Agent 怎么防提示词注入？ | 讲三层：结构分隔 + 指令数据分离 + 高危工具默认关闭。**并举一个你自己测出来的绕过案例** |
| 2 | Agent 调工具时怎么保证不越权？ | 身份透传（不用 Agent 自己的身份）+ 权限取交集 + 高危操作二次确认 |
| 3 | 用户让 Agent 删库，你怎么拦？ | 不靠 prompt 拦，靠**工具层**没有 delete 权限；靠人工确认点；靠 dry-run |
| 4 | Agent 陷入死循环怎么办？ | 三重上限（步数/Token/时长）+ 检测"连续两次相同动作" + 升级到人 |
| 5 | 怎么保证答案不瞎编？ | 引用绑定 + 置信度阈值 + 拒答。**关键是要有评测集证明拒答率与误拒率** |
| 6 | 多租户场景怎么隔离？ | 数据层（行级权限）+ 向量库（namespace）+ 运行时（沙箱）+ 密钥（按租户） |
| 7 | Agent 改了生产数据怎么回滚？ | 变更前快照 + 影响面预估 + 可撤销窗口 + 熔断阈值 |
| 8 | 你怎么评测安全性？ | 红队用例集（注入/越权/诱导）+ 攻击成功率 + 回归检测 |

## 6. 嵌进简历项目的 6 个动作（每个 1–2 天）

不要单独做一个"安全项目"，而是**把下面 6 件事做进你的主项目**，每件都能在面试里讲 3 分钟：

| # | 动作 | 产出 | 面试可讲点 |
|---|---|---|---|
| 1 | 加工具权限模型 | 一张"角色-工具-操作"矩阵 + 代码实现 | 权限取交集、越权拦截日志 |
| 2 | 提高危操作二次确认 | 一个确认 UI 或 CLI 交互 | 哪些操作算高危、怎么定义阈值 |
| 3 | 加全链路 Trace | Span 日志 + 一个 Trace 查看页 | 一次失败调用的完整链路复盘 |
| 4 | 建注入攻击用例集 | 20–30 条注入样本 + 攻击成功率 | 你测出过哪些绕过、怎么修的 |
| 5 | 做失败模式分类 | 一张 bad case 归因表（4 类） | 你项目最常见的失败模式是什么 |
| 6 | 加循环熔断 | 三重上限配置 + 触发统计 | 线上触发过几次、怎么优化的 |

> **性价比判断**：这 6 个动作合计约 1–2 周，但覆盖了 15.6%（越权）+ 10.6%（合规审计）+ 9.5%（可靠性）+ 2.8%（注入）的提及率。**是全部能力项里投入产出比最高的一组**。
